# 0023: Version storage and the draft/publish lifecycle

- **Status:** Accepted
- **Date:** 2026-11-09

## Context

Milestone 8 introduces drafts, version history, and publishing controls ([#146](https://github.com/handi7/lontar-cms/issues/146)). Editors must be able to:

1. Save unpublished drafts without altering live published content.
2. Publish and unpublish documents on demand.
3. Inspect previous revisions, compare diffs, and restore historical versions.
4. Benefit from background autosave without flooding the database with thousands of transient version rows.
5. Preview draft changes on a live frontend before publishing.

In ADR 0021 ([`docs/adr/0021-nested-field-storage.md`](0021-nested-field-storage.md) §7), we established that array and block items have stable string `id`s, and that complex fields are stored in a single JSON column. That eliminated child table explosion and established that version snapshots can store the full document as a self-contained JSON document.

However, several fundamental architectural questions must be resolved before writing any code:

1. **Table layout**: A dedicated versions table per collection vs. a single shared polymorphic versions table.
2. **Snapshot payload**: Whether top-level `group` fields are stored in their flattened database column format or their canonical nested object format.
3. **`_status` system field**: Its representation, default value, and reservation in `SYSTEM_FIELDS`.
4. **Storage model (Where the published row lives)**: Whether the parent collection table always holds the published document or the latest write, and how this impacts public read performance.
5. **Read semantics**: How `?draft=true` behaves, authorization requirements, `where` filtering, and `depth` relationship population.
6. **Retention and pruning**: How `versions: { maxPerDoc }` is enforced safely inside transactions.
7. **Autosave write volume**: How to handle frequent autosaves without exhausting retention or bloating storage.
8. **Lifecycle hook semantics**: Whether `afterChange` fires on draft saves, only on publish, or both.
9. **Globals**: How drafts and versions apply to single-document globals.
10. **Downstream compatibility**: How this design interacts with future localization (M11, [#149](https://github.com/handi7/lontar-cms/issues/149)).

## Decision

### 1. Table Layout: Dedicated Versions Table Per Collection

Each collection configured with `versions` receives a dedicated versions table named `${collectionSlug}_versions` (for example, `posts_versions`).

```
+-----------------------------------------------------------------------+
|                            posts_versions                             |
+------------------+------------------+---------------------------------+
| Column           | Type             | Purpose                         |
+------------------+------------------+---------------------------------+
| id               | int PK auto_inc  | Unique version ID               |
| parent_id        | int NOT NULL     | FK -> posts(id) ON DELETE CASCADE
| version_number   | int NOT NULL     | Monotonic revision index (1, 2) |
| snapshot         | json NOT NULL    | Complete canonical document     |
| _status          | varchar(20)      | 'draft' | 'published'           |
| autosave         | tinyint(1)       | 1 if generated by autosave      |
| created_at       | datetime/varchar | ISO 8601 creation timestamp     |
| created_by       | varchar(36) null | User ID of author (if auth)     |
+------------------+------------------+---------------------------------+
Indexes:
  - (parent_id, id DESC)
  - (parent_id, _status)
```

**Why dedicated tables over a shared table:**

- **Database-enforced referential integrity**: `parent_id` has a real `FOREIGN KEY REFERENCES ${collection}(id) ON DELETE CASCADE`. Deleting a document cleans up all historical versions at the database engine level atomically, with zero risk of orphaned rows.
- **Index isolation**: Queries for document history or draft checks scan only that collection's version rows, preventing high-write collections from degrading query performance across other collections.
- **Clean migrations**: Renaming or dropping a collection cleanly renames or drops its associated versions table.

For globals, each versioned global receives `${globalSlug}_versions` (e.g. `site_settings_versions`). Because globals have a single document, `parent_id` is omitted or fixed to `1`.

### 2. Snapshot Payload: Canonical Nested JSON

The `snapshot` column stores the entire document as a canonical, nested JSON object matching the shape returned by `findByID` / REST `GET`:

- Top-level `group` fields are stored in their nested object structure (e.g., `{ seo: { metaTitle: '...' } }`), **not** flattened into `seo__metaTitle` database column keys.
- Array and block items retain their stable string `id`s (ADR 0021 §2).
- The snapshot includes the document's content fields, `_status`, and the `createdAt`/`updatedAt` values at the moment the version was stamped.

**Why canonical nested JSON:**

- **One source of validation (Rule 5)**: When restoring an older version, the snapshot payload can be passed directly into the collection's Zod validation schema without any reverse-unflattening transformation.
- **Structural consistency**: Top-level `group` fields and groups nested inside blocks or arrays have the exact same object representation in the snapshot.
- **Deterministic diffing**: Storing stable IDs and nested objects makes semantic diffing in the admin UI ([#202](https://github.com/handi7/lontar-cms/issues/202)) straightforward and reliable.

### 3. `_status` System Field

When `versions: { drafts: true }` is enabled on a collection or global:

1. `_status` is added to `SYSTEM_FIELDS` ([`docs/adr/0004-system-fields.md`](0004-system-fields.md)) and reserved across all collections. Config definitions cannot declare a field named `_status`.
2. The TypeScript type of `_status` is `'draft' | 'published'`.
3. In the database, the parent collection table gains a `_status varchar(20) NOT NULL DEFAULT 'draft'` column with an index `(${collection}_status_idx)`.
4. If a collection does **not** have versions or drafts enabled, no `_status` column is created, and documents are implicitly published.
5. **Backfilling pre-existing documents when enabling drafts**:
   - Because existing documents created prior to enabling drafts were already live, they must remain published rather than hidden as drafts. When adding `_status` to an existing table, the migration must backfill existing rows:
     ```sql
     ALTER TABLE `<table>` ADD `_status` varchar(20) DEFAULT 'draft' NOT NULL;
     UPDATE `<table>` SET `_status` = 'published';
     ```
   - If migrating from an existing nullable column (such as renaming an earlier custom `status` column to `_status`), any `NULL` rows must be updated before applying `MODIFY COLUMN ... NOT NULL` to avoid MySQL strict mode failures:
     ```sql
     UPDATE `<table>` SET `_status` = 'draft' WHERE `_status` IS NULL;
     ALTER TABLE `<table>` MODIFY COLUMN `_status` varchar(20) NOT NULL DEFAULT 'draft';
     ```

### 4. Storage Model: Where the Published Row Lives

The parent collection table (`posts`) **always holds the currently published version** of the document (or the initial draft if the document has never been published):

```
                                  [ Editor Saves Draft ]
                                             │
                                             ▼
                 Does document have an existing published version?
                                ╱                         ╲
                             [YES]                       [NO]
                              ╱                             ╲
                             ▼                               ▼
               Write draft snapshot ONLY to         Write draft to parent table
                   `posts_versions`                 with `_status = 'draft'`
           (parent table remains 'published')       AND write snapshot to versions
```

The lifecycle proceeds as follows:

1. **Initial Draft (never published)**:
   - The document is inserted into the parent table with `_status = 'draft'`.
   - A corresponding version snapshot is inserted into `posts_versions` (`version_number = 1`, `_status = 'draft'`).
   - _Result_: The document receives its permanent, immutable integer `id` immediately. URLs (`/admin/collections/posts/:id`), upload relations, and parent foreign keys are established from day one.
2. **First Publish**:
   - The parent row is updated with the published field values, and `_status` becomes `'published'`.
   - A version snapshot is recorded in `posts_versions` with `_status = 'published'`.
3. **Editing an Already-Published Document (Draft Revisions)**:
   - When an editor modifies content and saves a draft, the parent row in `posts` is **not modified**. It retains its published data and `_status = 'published'`.
   - The draft changes are written strictly as a new snapshot in `posts_versions` with `_status = 'draft'`.
   - _Result_: The live website reading from `posts` continues serving the active published version without disruption.
4. **Publishing a Draft Revision**:
   - The latest draft snapshot from `posts_versions` is applied to the parent table row, setting `_status = 'published'` and refreshing `updatedAt`.
   - A new version row is recorded in `posts_versions` with `_status = 'published'`.
5. **Unpublishing**:
   - The parent table row has its `_status` changed to `'draft'`. Public queries immediately exclude it from results.
   - If a pending draft revision already exists in `_versions`, it remains the latest draft. Unpublishing does not overwrite or hide the pending draft behind a new draft version of the former published content. Subsequent draft reads (`?draft=true`) and the admin edit form continue to show the pending draft, while public reads (`draft: false`) exclude the document.
   - If no pending draft exists when unpublishing, a draft version is recorded for the unpublish event so the document's draft state is tracked in version history.

#### Why this model wins for read performance

In a headless CMS, public reads from frontend websites represent >99% of total traffic. By ensuring the parent collection table holds the published document:

- Public reads require **zero joins or subqueries** on `_versions`.
- Queries execute as simple `SELECT * FROM posts WHERE _status = 'published' AND ...`.
- All SQL column indexes (for `sort`, `where`, and relationships) operate directly on native database columns.
- The versions table is queried only when authorized editors request draft previews or view version history.

### 5. Read Semantics and Access Control

#### Authorization for `?draft=true`

- Requesting `?draft=true` (via REST API or Local API `{ draft: true }`) **requires update access** on the collection.
- If an unauthenticated or unauthorized client requests `?draft=true`, the request is rejected with `401 Unauthorized` or `403 Forbidden`. Unpublished drafts must never leak to unprivileged callers.

#### Public Reads (`draft: false` or omitted)

- Queries automatically filter by `_status = 'published'` on all collections with drafts enabled.
- Unauthenticated visitors never see documents in `_status = 'draft'`.

#### Draft Reads (`draft: true`)

- **Single document read (`findByID` / `GET /api/:collection/:id?draft=true`)**:
  - The engine checks `posts_versions` for the latest draft version for that `parent_id`.
  - If a newer draft exists in `posts_versions`, the engine returns the draft snapshot (with `_status: 'draft'`).
  - If no newer draft exists (the document in parent is already the latest write), the engine returns the parent document.
- **List queries (`find` / `GET /api/:collection?draft=true`)**:
  - The engine queries the parent table without the `_status = 'published'` constraint.
  - For any returned document that has a pending draft in `posts_versions`, the latest draft snapshot is hydrated.

#### Depth Population

- When querying with `draft: false` (public read):
  - Relationship and upload fields are populated strictly against published targets (`_status = 'published'`).
  - If a related document has only an unpublished draft, it resolves to `null` (for single relationships) or is omitted from the array (for `hasMany`), matching the graceful resolution of deleted records (ADR 0021 §4).
- When querying with `draft: true` (authorized editor read):
  - Related documents are populated with their latest draft state (subject to read/update permissions on the target collection).
  - Target collections only lift the `_status = 'published'` filter and hydrate their latest pending draft snapshot if the user has `update` access on that target collection.
  - If the user has `read` access but not `update` access on the target collection, the target is populated strictly in its published state (`_status = 'published'`), and any unpublished draft-only targets resolve to `null` (or are omitted from arrays).
  - This applies identically across collection documents and globals.

### 6. Retention and Version Pruning (`maxPerDoc`)

Collections and globals accept `versions: { drafts: true, maxPerDoc: 50 }`:

- `maxPerDoc` defaults to `50`. Setting `maxPerDoc: 0` disables pruning (unlimited revisions).
- **Transactional pruning**: Pruning executes synchronously within the same database transaction as the version write (ADR 0009):

```sql
DELETE FROM posts_versions
WHERE parent_id = ?
  AND id NOT IN (
    SELECT id FROM (
      SELECT id FROM posts_versions
      WHERE parent_id = ?
      ORDER BY id DESC
      LIMIT ?
    ) t
  );
```

Because pruning runs inside the transaction, version limits are strictly respected, and database storage never grows unbounded.

### 7. Autosave Write Volume Mitigation

In the admin SPA, autosave can trigger every few seconds while an editor types. Creating a new version row on every autosave would generate hundreds of rows an hour, exhausting `maxPerDoc` and purging meaningful history.

To prevent write bloat:

1. `posts_versions` includes an `autosave tinyint(1) NOT NULL DEFAULT 0` column.
2. Autosave requests pass `{ autosave: true }`. An autosave is always a draft write: the engine treats it as `draft: true` even when the request omits `draft`, so it can never reach the live row.
3. **In-place update strategy**:
   - If the most recent version for `parent_id` is already a draft with `autosave = 1`:
     - The engine **updates that existing autosave row in place** (updating `snapshot`, `updated_at`, and `created_by`).
   - If the most recent version was a manual action (`autosave = 0`):
     - The engine inserts a single new row with `autosave = 1`. Subsequent continuous autosaves update this new row in place.
   - When the editor explicitly clicks "Save Draft" or "Publish":
     - The engine creates a permanent version row with `autosave = 0`.

This guarantees that an entire continuous editing session generates at most **one** transient draft row in the versions table.

### 8. Lifecycle Hooks and `afterChange` Semantics

The question of whether `afterChange` runs on draft saves or only on publish is settled as follows:

`beforeChange` and `afterChange` run on **both draft saves and publishes**.

To allow hook implementations to distinguish between operations, hook arguments include `status`, `previousStatus`, and `statusTransition`:

```ts
export interface HookArgs<T> {
  doc: T
  previousDoc?: T
  operation: 'create' | 'update'
  status: 'draft' | 'published'
  previousStatus?: 'draft' | 'published'
  statusTransition?: 'draft' | 'published' | 'publish' | 'unpublish'
}
```

**Benefits**:

- Internal hooks (such as audit logging, draft preview indexing, or revision notifications) can process all updates.
- External hooks (such as sending newsletters, triggering public webhooks [#197](https://github.com/handi7/lontar-cms/issues/197), or invalidating edge CDN caches) can cleanly guard against draft updates:
  ```ts
  afterChange: async ({ statusTransition }) => {
    if (statusTransition === 'publish') {
      await triggerDeployWebhook()
    }
  }
  ```

### 9. Globals

Globals support the same versioning and publishing options:

```ts
const SiteSettings = global({
  slug: 'site-settings',
  versions: { drafts: true, maxPerDoc: 20 },
  fields: { ... },
})
```

- Each versioned global gets `${globalSlug}_versions` (e.g. `site_settings_versions`).
- The global table stores the live published settings; drafts live in the versions table.
- REST endpoints:
  - `GET /api/globals/site-settings?draft=true`
  - `POST /api/globals/site-settings?draft=true`
  - `POST /api/globals/site-settings/publish`
  - `POST /api/globals/site-settings/unpublish`

### 10. Downstream Compatibility with Localization (M11)

In Milestone 11 ([#149](https://github.com/handi7/lontar-cms/issues/149)), fields can be marked `localized: true`.

Because the `snapshot` column stores the canonical JSON representation of the entire document, localization is fully compatible without changing the versions table schema:

- Localized fields in the snapshot simply store their localized dictionary or nested localized values (e.g. `{ title: { en: 'Hello', id: 'Halo' } }`).
- Draft and publish lifecycles remain identical.

## Alternatives Considered

1. **Single shared `_versions` table for all collections:**
   - _Why rejected_: A single table cannot enforce native database foreign keys (`ON DELETE CASCADE`) to parent documents, leading to potential orphan data. Furthermore, all version writes serialize on the same database indexes, creating a major write bottleneck across unrelated collections.
2. **Parent table always holds latest write, with `_status` column:**
   - _Why rejected_: If saving a draft on an already-published document updates the parent row to `'draft'`, public queries on the live site would either return nothing (hiding the live article) or be forced to fall back to scanning JSON snapshots in `_versions`. Falling back to `_versions` for public reads destroys SQL sorting, filtering, and query caching performance.
3. **Appended row on every autosave:**
   - _Why rejected_: An editor actively drafting an article would generate hundreds of database rows per hour, rapidly exceeding `maxPerDoc` and flushing meaningful historical versions.
4. **Firing `afterChange` only on publish:**
   - _Why rejected_: Prevents legitimate use cases like updating internal draft search indexes or tracking editor activity. Passing explicit `status` and `statusTransition` parameters gives developers full clarity and control.

---

## Consequences

### Easier

- **Fast public reads**: Public traffic never joins or scans the versions table; native SQL indexes and execution plans remain intact.
- **Data integrity**: Version history tables are strongly linked via foreign keys with `ON DELETE CASCADE`.
- **Safe autosave**: Continuous background saves never flood version history or retention budgets.
- **Accurate diffing**: Stable IDs from ADR 0021 make comparing array and block changes straightforward in the admin UI.

### Harder

- **Hydration on draft queries**: Reads with `?draft=true` require checking `_versions` for newer draft snapshots and merging them over parent rows.
- **Filter synchronization on drafts**: Searching and filtering in the admin list view primarily runs against parent table columns; documents with newer draft titles in versions are hydrated after the parent query executes.

## Public API (Spec for README.md)

### Collection & Global Config

```ts
import { collection, fields as f } from '@lontar/core'

const Posts = collection({
  slug: 'posts',
  // Enable versions and drafts
  versions: {
    drafts: true,
    maxPerDoc: 50, // default 50, set 0 for unlimited
  },
  fields: {
    title: f.text({ required: true }),
    content: f.richText(),
  },
})
```

### Local API

```ts
// Public read: returns published documents only (_status === 'published')
const { docs } = await lontar.find('posts')

// Draft read (requires update access): includes latest drafts
const { docs } = await lontar.find('posts', { draft: true })

// Find by ID with draft
const post = await lontar.findByID('posts', 1, { draft: true })

// Create draft
const draftPost = await lontar.create('posts', data, { draft: true })

// Publish document
await lontar.publish('posts', 1)

// Unpublish document
await lontar.unpublish('posts', 1)

// Version history
const versions = await lontar.findVersions('posts', 1)
const restored = await lontar.restoreVersion('posts', 1, versionId)
```

### REST API

```http
# Public read (published only)
GET /api/posts

# Read with drafts (requires update access)
GET /api/posts?draft=true
GET /api/posts/1?draft=true

# Save draft
POST /api/posts?draft=true
PATCH /api/posts/1?draft=true

# Publish / Unpublish actions
POST /api/posts/1/publish
POST /api/posts/1/unpublish

# Version history
GET /api/posts/1/versions
POST /api/posts/1/versions/:versionId/restore
```
